# HIVE local coding-agent operating instructions

## Objective

Implement the research and runtime framework described by 00_START_HERE.md, 01_Framework.md, 07_Local_Build_Roadmap.md, and 08_Local_Coding_Agent_Handoff.md. Preserve Ian's broader HIVE goal and all competing research paths.

## Grounding

- Read relevant prior methods and source history before changing a conclusion.
- Inspect the actual PC. The inventory is a 15 November 2026 snapshot.
- Treat Graphy as likely Graphify until the local project is identified.
- Confirm D:/MIcroMillionaire before integrating with the existing vault.
- Discover exact SOL, Grok, and Nemotron endpoints; do not infer their availability or locality from installed CLI software.
- Reuse established repositories and tools where they satisfy the contract.

## Parallel ownership

Use a separate Git worktree per code worker and a single integration owner. Assign bounded tickets with owned paths, input versions, outputs, budgets, and acceptance criteria. Do not overwrite another worker's branch. Research workers propose records; the evidence integrator maintains canonical IDs.

## Evidence rules

- Separate proposal, implementation, execution, measurement, and interpretation.
- Record primary sources and exact versions.
- Keep observed, inferred, historical, and synthetic material distinguishable.
- Preserve contrary results and inactive branches with reopening conditions.
- Never label an estimate or simulation as a real GPU/model measurement.
- Do not treat old project success/failure labels as fresh evidence.
- Retain 100, 1000, and 10000 logical-expert research paths; measure active concurrency.
- A two-model prototype is not a limit on HIVE architecture.

## Experiment rules

Use the experiment pages and declare fidelity, data access, external feedback, active and total capacity, compute, latency, and all persistent storage. Separate current-only wake schedules from total learning that includes offline rehearsal. Compare blocked replay, expansion, distillation, and dreaming as distinct mechanisms.

Preserve all raw results, failures, seeds, task orders, versions, and stopped runs. Do not repeatedly tune on a sealed evaluation set. Change a branch's conclusion only within its tested scope.

## Improvement rules

Each update states whether it changes external memory, procedures, routing, parameters, topology, or protocols. Train candidates separately from serving artifacts. Publish the tested compatible version set after declared gates; keep rollback artifacts within the storage ledger.

A recurring intervention should become a tested rule, tool, workflow, or local supervisor when useful. Keep stronger parametric and organizational learning paths active as isolated research.

## Data and graph rules

Markdown notes are the human research record. Graphify output is derived and rebuildable. Runtime events and model manifests are separate authorities.

Preserve original archive bytes. Use stable IDs and relative links. Relations such as motivated_by, challenged_by, different_scope, and tested_by have distinct meanings. A visual edge or high model confidence is not proof.

## Local implementation boundary

This is a build plan, not an instruction to post videos, send messages, make purchases, or operate live external accounts. Use recorded fixtures or dry runs for those integration tests until the actual workflow authorizes execution.

Then perform only the relevant code/runtime checks for the changed capability. Report what was actually run, the result, and remaining uncertainty.
